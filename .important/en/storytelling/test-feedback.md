## Agent calibration and matching

During the **v0.1.0-rc** phase (prototype) and then across the whole
beta.1 → beta.2 cycle, we tested Standardoc with several AI agents
available at the time. **The observed behaviors are very uneven across
agents.**

### The agents that don't match

Three recurring patterns observed on agents that don't naturally align
with Standardoc's architecture:

- **Shortcut to `grep + read`** — the agent knows MCP, but the moment
  the task gets complicated, it switches to `Bash` / `Grep` / `Read` by
  reflex. Without a PreToolUse hook to block it, the MCP-first protocol
  stays a non-observable good intention.
- **Ignores the `routing_hint`** — when an agent calls `get_context(fqdn,
  depth=2)` without having done `depth=1` recently (within the last 5
  minutes) on the same FQDN, the response contains a corrective
  `routing_hint` that reminds it to map first in `depth=1` before
  drilling in `depth=2`. That's the only case where the hint appears —
  it's a one-off corrective signal, not a general guidance system. Some
  agents ignore it and keep going in `depth=2` by default, the result:
  a full drill where a cheap map would have been enough to eliminate 80%
  of the neighbors.
- **Unstructured exploration** — the agent burns 100% of the budget on
  iterative searches without carrying anything over. No reuse of
  already-visited symbols, no `check_stale` to reuse a cache.

### The agent that matches best

**[Claude Code](https://www.anthropic.com/claude-code) in Opus mode**, a
1M-token window, with an effort tier that varies by task (medium / high
/ extra-high — never fixed). It's on this agent that Standardoc's
calibration is done:

- PreToolUse / SessionStart hooks that enforce the MCP-first guardrail
- The `get_context` `routing_hint` respected in practice (Opus maps in
  `depth=1` before drilling in `depth=2` instead of taking the
  corrective)
- The `signature_only` / `strip_attrs` knobs of `get_body` used
  spontaneously when the context budget gets tight

The other agents work, but without the same fluidity, and with
consumption gaps we don't observe with Opus.

### A few dogfood estimates

Standardoc indexing itself, Claude Code Opus sessions: early on, most of
the 5h quota went to redundant exploration (grep, re-reading, rediscovering
already-visited structures); now the same window lasts on the order of two
work sessions. Rough dogfood estimates, not controlled benchmarks — they
assume a dev who masters their code and applies the 3-phase discipline.

### What genuinely impressed in dogfood

Beyond the numbers, the most striking qualitative observation: **the
code generated by the agent rarely breaks, and spontaneously respects
the project's architecture and style**. The tacit conventions — naming,
module granularity, error style, IR / storage / query / providers
separation of concerns — are picked up by the agent without us having
to re-explain them on every task.

It's exactly what a shared graph coupled with an encoded discipline
should produce: **an agent that conforms to the project rather than
crushing it.**

**But that doesn't exempt you from review.** A maintainable project
demands that the dev **knows their code and understands it** — not just
that an agent can produce code that passes the tests. Review stays
mandatory on every PR, on every work item. Standardoc makes review
*faster and more reliable* (the agent follows the conventions, so fewer
surprises on the reviewer's side); it does *not* replace it.

### Disclaimer: tripartite calibration

**We don't guarantee your agent will match the same way.** Standardoc
provides the infrastructure (graph + MCP + discipline); if your agent
doesn't respect the MCP-first protocol or ignores the `routing_hint`
corrections when it violates the `depth=1 → depth=2` pacing of
`get_context`, you'll only get part of the gains. **The calibration is
tripartite**: infrastructure + agent + operator.

#### What the infrastructure already provides

- **An auto-generated skill template** (a `SKILL.md` written into
  `.claude/skills/standardoc/`) — teaches the agent the tool fallback
  hierarchy (Standardoc → LSP → Read / Grep), the 3-phase protocol
  (Explore → Target → Drill), the edge kinds, and the language coverage.
  The agent that reads it at boot doesn't have to guess the mechanics.
- **MCP-first hooks** (on the Claude Code side) — PreToolUse blocks
  `Bash` / `Read` / `Grep` / `Glob` until a Standardoc tool has been
  called in the session; SessionStart wipes the sentinel on every new
  chat. Observable discipline, not good intention.

#### What stays the operator's job

Three non-delegable human responsibilities:

1. **Couple your agent to Standardoc.** Install the VSCode extension
   (which generates the skill and writes `.mcp.json` automatically via
   the opt-in init flow) or wire `.mcp.json` by hand for another MCP
   client. If the agent doesn't see Standardoc, it doesn't use it.
2. **Architect your project with a minimum of coherence.** Standardoc
   indexes what exists — if the codebase is spaghetti with no clear
   modules, the graph reflects the spaghetti. The tool amplifies what
   the operator cultivates; it doesn't replace it.
3. **Tell the agent when and how to use the tools.** The skill template
   teaches the general mechanics; but for a given task, it's up to the
   operator to say *"start with `find_symbol`"*, *"first check who calls
   X"*, *"don't grep here"* — especially early in calibration, before
   the agent has internalized the pacing habits on its own.

If your default agent is bad at this protocol, the option that works in
practice is: (a) force MCP-first on it via the Claude Code hooks
(guardrail), and (b) let it absorb, over 2-3 tasks, the `routing_hint`
corrections when it skips the `depth=1 → depth=2` pacing of `get_context`.

## What we dropped

Several early leads were killed or pushed back — the `{{ @doc.X }}`
templating DSL, the `materialize` command, a separate `standardoc-server`
binary, the `.standardoc.json` config, `cargo install` as the sole channel,
and the RAG / sessions layers (in beta.3). The full list with reasons lives
in [TODO-LIST → Deferred / killed](../TODO-LIST.md#deferred--killed).
